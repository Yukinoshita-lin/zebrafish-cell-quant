## 0. 先搞清楚我们在做什么

一句话：**在荧光显微图里找出「中后肠」区域，然后只在这个区域里数荧光细胞。**

整条链路分两段，**训练只针对第一段**：

```
单帧荧光图 (2752×2208)
   │  取绿色通道，÷4 下采样
   ▼
U-Net 分割  ──► 中后肠掩码      ← 【模型训练的就是这一段】
   │
   ▼
经典检测（草稿框）+ 掩码过滤 ──► 细胞计数
```

关键认知：**计数环节本身不训练**。它复用已有的检测框（`annotations/drafts/*.txt`），
模型只负责「这块区域算不算肠」。所以 Dice 提升会直接改善计数，但计数偏差也受检测框质量影响。

验收标准：**test Dice ≥ 0.85**（需求 7）。

## 1. 动手前必读：三个最容易踩的坑

### 坑 1：以为这台机器没有 GPU

判断依据不能看 `torch.__version__` 的后缀，要直接问硬件：

```bash
nvidia-smi                                        # 看有没有卡、驱动支持到哪个 CUDA 版本
python -c "import torch; print(torch.cuda.is_available(), torch.__version__)"
```

本机实际情况：**RTX 4060 Laptop（sm_89，8.6GB，驱动支持 CUDA 13.1）**。

如果 `torch.cuda.is_available()` 是 `False` 但 `nvidia-smi` 有卡，说明 torch 装成了 CPU 版
（`+cpu` 后缀），需要换装：

```bash
# 注意：先把临时目录指到 F 盘，C 盘只剩 9GB，2GB 的 wheel 临时解压会撑爆
export TMPDIR="F:/tmp_pip" TMP="F:/tmp_pip" TEMP="F:/tmp_pip"
pip install --no-cache-dir torch==2.14.1+cu130 \
    --index-url https://download.pytorch.org/whl/cu130
```

**CPU 与 GPU 的差距是 37 倍**（338 s/epoch vs 9 s/epoch）。装错了会白等几小时。

### 坑 2：前景只占 0.32%

中后肠在画面里只占 **0.32%** 的像素。如果损失函数用普通 BCE，
模型会直接学到「全预测背景」——因为这样 loss 就很低。

所以损失必须是 **加权 BCE（`pos_weight=20`）+ SoftDice**。这两项已在脚本里，**不要删**。

### 坑 3：默认参数 ≠ 推荐参数

脚本里的默认值是"能跑"的保守配置，**不是**最优配置。几个关键差异：

| 参数 | 默认值 | 推荐值 | 原因 |
|---|---|---|---|
| `UNET_NORM` | `bn` | **`gn`** | BatchNorm 在小数据集上 train/eval 统计失配，Dice 会剧烈震荡；换 GroupNorm +0.030 |
| `UNET_DEPTH` | `3` | **`4`** | 多一级解码，边界更准 |

其余参数默认值基本可用。**最容易出错的是 `UNET_BATCH=8`——用 gn 时会 OOM，必须降到 4。**

**所以不要直接 `python tools_train_unet_v3.py`，要按 §4 的推荐命令跑。**

## 3. 数据长什么样

所有标注信息在 `annotations/manifest.csv`（UTF-8 with BOM）：

| 列 | 含义 |
|---|---|
| `name` | 样本名，如 `260903_Ⅲ-1_Snap-40938` |
| `batch` / `group` | 实验批次 / 分组 |
| `stratum` | `处理` / `造模` / `对照` |
| `split` | **`train` 或 `test`** ← 训练只读这一列 |
| `src_tif` | 原图绝对路径 |
| `mask_png` | 人工掩码路径 |
| `mask_area_pct` | 掩码占全图百分比（正常约 0.3） |

掩码图在 `annotations/masks/<name>.png`，白色为前景。

当前数据集：**190 张（train 150 / test 40）**，4 个批次，
分层为 处理 104 / 造模 48 / 对照 38。

⚠️ **划分是按图做的，不是按 patch**。一张图只会出现在 train 或 test 之一，
不存在同图泄漏。**不要自己重新划分**，否则和别人的结果没法比。

## 4. 训练一个模型

### 4.1 第一步永远是自检增强

长训练前先跑这个，**成本 1 分钟，能避免几小时的算力白费**：

```bash
python tools_check_aug.py
```

它会检查增强（旋转/翻转/仿射/亮度抖动）之后，**掩码是否仍落在高亮区域**。
如果增强把 x 和 y 错位了，训练曲线看起来完全正常，但模型学的是错的东西——
这种 bug 只能靠这个检查提前发现。

输出 `PASS` 才能继续。

### 4.2 先跑通：60 轮，约 12 分钟

第一次先别冲指标，用短配置确认链路能跑通：

```bash
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True

UNET_EPOCHS=60 UNET_BASE=32 UNET_DEPTH=4 UNET_NORM=gn UNET_AUG_DECAY=0 \
UNET_BATCH=4 UNET_SCALE=4 UNET_LR=0.0015 \
python tools_train_unet_v3.py
```

**实测基线（可用来对照你的环境是否正常）：test Dice = 0.6958，耗时 12 分钟。**

这个分数不高是**正常的**——60 轮远不足以收敛（最佳轮次=第 60 轮，说明还在爬）。
它的作用只是验证环境、数据、模型、损失全部正确。判断标准：

- 日志里 loss 从约 1.19 稳定降到 0.40 左右
- Dice 从 0.01 一路爬升到 0.69 左右
- 报告里 `最佳 epoch: 60`（末轮，符合欠训练预期）

若你的数字明显偏离（比如 loss 不降、Dice 卡在 0.0x），说明环境或数据有问题，别急着加轮数，先查 §6。

输出产物：

| 文件 | 内容 |
|---|---|
| `annotations/unet_model_v3.pt` | 最佳权重（含 state_dict / scale / base / depth / norm / epoch / dice） |
| `annotations/unet_resume_v3.pt` | 续训状态（模型+优化器+调度器+EMA） |
| `annotations/unet_metrics_v3.txt` | 训练报告 |
| `annotations/unet_vis_v3/*.png` | 最好/最差各 3 张的可视化（绿=GT 红=预测 黄=重合） |

### 4.3 冲指标：400 轮，约 84 分钟

确认链路没问题后，跑正式配置（这是实测最优的单阶段配置）：

```bash
UNET_EPOCHS=400 UNET_BASE=32 UNET_DEPTH=4 UNET_NORM=gn UNET_AUG_DECAY=1 \
UNET_BATCH=4 UNET_SCALE=4 UNET_LR=0.002 \
python tools_train_unet_v3.py
```

预期 test Dice **0.832 左右**（实测 0.8320）。

⚠️ **这条配置的曲线会在 epoch 220 左右见顶，之后缓慢回落**（末尾约 0.805）。
这是增强退火带来的轻微过拟合，**属于预期行为，不要中断**——
脚本保存的是历史最佳检查点，回落不影响最终产物。详见 §6。

想省时间可以用 250 轮版本，约 54 分钟，Dice 0.8288，曲线全程平稳：

```bash
UNET_EPOCHS=250 UNET_BASE=32 UNET_DEPTH=4 UNET_NORM=gn UNET_AUG_DECAY=0 \
UNET_BATCH=4 UNET_SCALE=4 UNET_LR=0.0015 \
python tools_train_unet_v3.py
```

> 想要更高：见 §7「已经试过、有效的提升手段」。单阶段很难过 0.85，需要集成或补数据。

### 4.4 参数全表

| 环境变量 | 默认 | 推荐 | 说明 |
|---|---|---|---|
| `UNET_EPOCHS` | 150 | 250 | 轮数。曲线未见顶就继续加 |
| `UNET_BASE` | 32 | 32 | 基础通道数。**显存和它平方相关** |
| `UNET_DEPTH` | 3 | **4** | 下采样级数，4 比 3 好 |
| `UNET_NORM` | bn | **gn** | `bn` / `gn`。小数据集必用 gn |
| `UNET_BATCH` | 8 | **4** | ⚠️ 用 gn 时**最多 4**，8 会 OOM（见 §6） |
| `UNET_SCALE` | 4 | 4 | 下采样倍率。4→688×552；3→917×736（更慢更精细） |
| `UNET_LR` | 2e-3 | 1.5e-3 | 学习率，配 warmup + cosine |
| `UNET_AUG_DECAY` | 1 | 1 | 1=后期把增强强度降到 0。会让曲线见顶后回落（最佳检查点不受影响）；0=全程保持增强，曲线更平稳 |
| `UNET_RESUME` | 1 | 1 | 自动从 `unet_resume_v3.pt` 续训 |
| `UNET_SEED` | 0 | 任意 | 换种子可获得集成多样性 |
| `UNET_INIT` | 空 | — | 从指定权重初始化（跨分辨率微调用） |
| `UNET_CUDA` | 1 | 1 | 设 0 强制走 CPU（仅调试） |

### 4.5 断点续训（本机必用）

这台机器会过夜休眠，**训练进程会被冻住**。脚本为此做了两件事：

1. 每 5 轮把 model / optimizer / scheduler / EMA 全状态存进 `unet_resume_v3.pt`
2. 启动时自动检测并恢复（日志会打印「断点续训：从 epoch N 恢复」）

所以你**不需要手动做什么**——重跑同一条命令就行。
但配置必须完全一致（epochs/base/depth/scale/norm 都参与校验），不一致会从头训。

## 5. 怎么看结果

打开 `annotations/unet_metrics_v3.txt`。下面是一次真实训练的样例（v4_gn，400 轮）：

```
测试集 Dice @0.5: 均值 0.8320  中位 0.8440  P10 0.7553
最佳阈值 0.65 -> Dice 0.8327（较 @0.5 +0.0007）
面积比中位 1.05  过分割(>2x) 0 张  欠分割(<0.5x) 0 张
Dice 分布: 0.0-0.2:0张  0.2-0.4:0张  0.4-0.6:1张  0.6-0.8:10张  0.8-1.0:29张
```

**读法：**

- **均值 vs 中位差距大** → 有长尾差样本，去看 P10
- **P10 很低** → 少数图彻底失败，是数据/标注问题，加轮次救不了
- **面积比中位 ≈ 1.0** → 尺度校准正常；持续 >1.5 是过分割，<0.6 是欠分割
- **Dice 分布全挤在 0.4~0.6** → 典型**欠拟合**，加大模型/加轮次
- **最佳 epoch ≠ 最后一轮且之后下降** → **过拟合**，减轮次或加正则

## 6. 出问题怎么查：先诊断，再改

**不要凭感觉调参。** 先跑诊断脚本拿到事实：

```bash
DIAG_MODEL=unet_model_v4_gn.pt python tools_diagnose.py
```

它会输出阈值扫描 + 逐图分布 + 面积比，并直接告诉你失效模式。

### 症状 → 处方对照表

| 症状 | 判据 | 处方 |
|---|---|---|
| 阈值/后处理问题 | 阈值 0.3~0.7 扫描 Dice 变化 < 0.01 | **改不了，别调了**（阈值几乎不是瓶颈） |
| 标注有噪声/不可学 | 存在大量 Dice < 0.2 的图 | 改数据/标注，加轮次无用 |
| 分辨率卡死 | 见下方「分辨率天花板」检查 | 提高分辨率（`UNET_SCALE=3`） |
| **欠拟合** | 无灾难失败 + 分布挤在中段 + 最佳轮次=末轮 | **加容量 + 加轮次** |
| **过拟合** | 最佳轮次在中途，之后持续下降 | 减轮次 / 关增强退火 / 加正则 |

「分辨率天花板」怎么测——把**人工掩码**下采样再上采样回原图，和原掩码比 Dice，
这就是「完美预测」在该倍率下的上限：

| 倍率 | 天花板 |
|---|---|
| ÷2 | 0.9861 |
| ÷3 | 0.9784 |
| **÷4** | **0.9699** |
| ÷6 | 0.9551 |

÷4 的天花板 0.97 远高于 0.85 → **分辨率不是当前瓶颈**，不要急着上调。
（`python tools_res_ceiling.py` 可重跑）

### 常见报错

**`CUDA driver error: out of memory`（在 `dec(torch.cat(...))` 处）**

不是显存"不够"，是配置超了 8GB 上限。按顺序试：

1. **`UNET_BATCH` 从 8 降到 4** ← 最常见，GroupNorm @batch8 峰值 8.37GB 就超了
2. 降 `UNET_BASE`（32→24）
3. 降 `UNET_DEPTH`（4→3）
4. 加 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`

**两个进程同时跑必有一个 OOM。** 训练前先确认：

```bash
nvidia-smi                  # 看显存占用
```

如果还有别的 `python.exe` 占着卡，先关掉。

**评估阶段 OOM**

评估会一次性跑 40 张测试图。脚本已按像素预算自动分块（chunk ≤ 8），
如果你自己写推理代码，**务必也分块**——整批 40 张 552×688，单层激活就要 1.8GB。

## 7. 已经试过、有效的提升手段

按投入产出比排序（都是本项目实测）：

| 手段 | 收益 | 说明 |
|---|---|---|
| **补标注数据** | 最大 | train Dice 0.8666 已过线，test 0.8349 未过 —— 瓶颈是**泛化**，不是模型能力 |
| 加容量（base16→32, depth3→4） | **+0.22** | 0.58 → 0.80，提升最大的一步 |
| GroupNorm 替代 BatchNorm | **+0.030** | 消除训练曲线震荡（0.8021 → 0.8320） |
| TTA（8 向翻转旋转平均） | **+0.013** | 推理时做，零训练成本（0.7974 → 0.8104） |
| 多模型集成 | +0.004/个 | **异构性比强弱更重要**：加入较弱的 BN 模型反而更好 |
| clean_mask 后处理 | +0.001 | 几乎可忽略 |
| ÷3 微调（从 ÷4 权重初始化） | **≈0** | 单模型无提升（0.8311 vs 0.8320），真正价值是**作集成成员提供分辨率多样性** |
| 提高分辨率 ÷4→÷3 | 边际 | 天花板 0.97 已够，单靠它提不上去 |
| 调阈值 | ~0 | **别做** |
| `largest_component` 后处理 | **-0.014** | **有害**（见 FAQ），除非你只优化计数指标 |

### 集成怎么做

```bash
# 推理时把多个模型的概率图平均（自动按各自 scale 预处理，再重采样对齐）
V2_MODELS="unet_model_v3_bn.pt,unet_model_v4_gn.pt,unet_model_v5_gn2.pt,unet_model_v6_gn3.pt" \
V2_TAG=ens4 python tools_v2_count.py

# 单独比较各组合的 Dice
python tools_ensemble.py
```

### ÷3 微调怎么做

用途：**不是**为了单模型涨分（实测 0.8311 vs 0.8320，反而略低），
而是产出一个「不同分辨率」的模型加入集成——跨分辨率组合的中位数和达标率最优。

```bash
# 从 ÷4 的权重出发，切到 ÷3 分辨率短跑 60 轮（卷积权重与分辨率无关，可直接加载）
UNET_EPOCHS=60 UNET_BASE=32 UNET_DEPTH=4 UNET_NORM=gn UNET_AUG_DECAY=0 \
UNET_SEED=2 UNET_BATCH=2 UNET_SCALE=3 UNET_LR=0.0003 UNET_RESUME=0 \
UNET_INIT=unet_model_v4_gn.pt python tools_train_unet_v3.py
```

⚠️ 注意 `UNET_RESUME=0`（不能续训，因为 scale 变了会校验不一致），
且 `UNET_BATCH=2`（÷3 像素量是 ÷4 的 1.78 倍，batch 4 会 OOM）。

## 9. FAQ

**Q：为什么计数脚本里 `largest_component` 默认是关的？**
A：它会把 GT 里合法的**碎片状肠道段**整段删掉，Dice 从 0.8104 掉到 0.7966。
但对**计数**指标反而有利（r 0.901 vs 0.883）——因为能滤掉假阳性检测。
两个指标方向相反，按你的验收口径选：`V2_LARGEST=1` 打开。

**Q：上采样掩码用什么插值？**
A：**必须 `INTER_NEAREST`**。÷4 口径实测 nearest 0.9699 vs linear 0.9274，
linear 会把边界抹糊，白丢 4 个点。

**Q：为什么 EMA 有时显示 0.0000？**
A：正常现象。EMA 用 decay=0.995，前期还是随机初始权重主导；
这个深模型在 EMA 收敛前会输出空掩码。约 100 轮后恢复正常并通常反超 raw。
**不要因此判定 EMA 坏了**（逻辑有单元测试：`python tools_test_ema.py`）。

**Q：训练要多久？**
A：GPU 下 base32/depth4/÷4 约 **12 s/轮**（batch 4）。
250 轮 ≈ 54 分钟；400 轮 ≈ 84 分钟。CPU 要慢 37 倍（338 s/轮），别试。

**Q：能同时开两个训练吗？**
A：**不能。** 8GB 显存下两个进程必有一个 OOM。要并行训练请等一个跑完。

**Q：训练曲线在后期回落了，是训练失败吗？**
A：不一定。`UNET_AUG_DECAY=1`（默认）会让最后 25% 训练的增强强度线性降到 0，
本意是「在更接近真实的数据上收敛」，副作用是最需要正则化的阶段撤掉了正则化，
于是曲线在见顶后缓慢回落。实测两种设置：

| 设置 | 峰值 | 末尾 | 曲线形态 |
|---|---|---|---|
| `AUG_DECAY=1` | **0.8320**（epoch 220） | 0.8045 | 先高后降 |
| `AUG_DECAY=0` | 0.8288 | 0.8270 | 全程平稳 |

**两者最终产物差距在种子波动范围内**，而脚本始终保存**历史最佳**检查点，
所以回落不会毁掉结果。判断方法只看一点：日志里有没有出现「best 更新」。
如果最佳始终停在某一轮没再涨、且末尾明显更低，那才是过拟合，可以减轮数或设 `AUG_DECAY=0`。

**Q：为什么 train Dice 0.8666 已经过线，还要补数据？**
A：train 过线说明**模型表达能力够了**；test 只到 0.8349 说明**泛化不足**，
即 150 张训练图覆盖不了真实变异。这种情况继续加模型收益递减（每个约 +0.004），
补标注才是根本解。

**Q：改了代码怎么验证没搞坏？**
A：四条底线检查：
1. `python tools_check_aug.py` → 增强对齐
2. `python tools_test_ema.py` → EMA 逻辑
3. 短训 60 轮 → Dice 应在 **0.69 左右**（实测基线 0.6958）
4. `python tools_ensemble.py` → 各模型分数应和记录一致

|---|---|
| Dice | 分割重合度，`2|A∩B| / (|A|+|B|)`，1 为完美 |

| EMA | 权重指数滑动平均，抑制训练噪声 |
| 深监督 | 解码每一级都接一个输出头，逼浅层也学判别特征 |
| P10 | 第 10 百分位，用来看"最差的那批图有多差" |
